# 普通终端原生 App 实测证据

## 结论与边界

【事实】主验收代理通过 CUA 在正式「小陈的画布」App 内运行本地探针，本专项代理随后独立读取 6 份 JSON、4 份进程采样，并核对探针源码。测试工作目录均为隔离片子 `/Users/chenhuajin/项目/视频制作台/AI编导/独立验收-QA-urRtjA`，没有模型请求。

【事实】6 轮共生产 31457118 字节有限编号内容，62 次 DSR 全部成功，0 超时、0 报告异常、0 中断。DSR 表示“输出经过 PTY/Tauri 到 xterm 解析，再由终端答复回到 PTY”的往返；不是屏幕绘制完成、帧率，也不证明 31 MB 每一行均已肉眼或逐字对比。

【事实】在每秒 512 KiB 持续输出期间，最后一轮确实收到 `A`、`B`、`C`、回车各一次，按键回显之后的解析往返为 2.34–20.07 ms。这一强度下没有出现探针输入不达或 DSR 卡死。

【未知】更长时间或更高持续流量的表现、实际物理键盘到画面呈现的完整延迟、终端与大媒体画布同时交互的帧率，不能由本次有限测试推定。

## 输入核验与自动化工具限制

【事实】最初使用 CUA `pressKey` 输入裸字母时，辅助功能界面曾显示输入框 Value 为 `abc`，但对应探针 `keys=[]`。设置或看到隐藏输入框的 value，并不证明字符已作为终端输入事件送入 PTY。

【事实】独立把真实探针的 `onData`/`key` 函数加载进内存测试，四种情况均准确记录 `a,b,c`：一次传入 abc、分三次传入、先分块传入 DSR 回答再接 abc、普通字母与 DSR 混合。源码 `native-terminal-probe.mjs:112–125` 只识别完整的光标报告与等待未完成的 ESC 前缀，不会把普通 ASCII 吞掉；`:104–108` 先记录字符，再发回显。

【事实】最后改用 CUA `typeText('ABC')` 加 Return，在真实持续输出中得到：

| 字符 | 程序开始后收到的时间 | 回显后 DSR 往返 |
| --- | ---: | ---: |
| A | 531.66 ms | 20.07 ms |
| B | 541.60 ms | 3.74 ms |
| C | 552.23 ms | 8.34 ms |
| 回车 | 569.58 ms | 2.34 ms |

【事实】主验收代理的 CUA 输入调用开始于 `08:42:43.709Z`，结束于 `.775Z`；探针起点为 `.214Z`，A 于起点后 531.66 ms 收到。两份时钟粗对齐约 36.7 ms，包含自动化输入开销，不能报成物理键盘精确延迟。B 的 DSR 还排在 A 的请求之后；单个 DSR 往返也不等于完整按键回显耗时。

【推断】最初的 keys 为空应归为该 CUA 注入方式未证实到达 PTY，而非产品键盘输入失败。最后一轮已给出输入字节真实到达的正面证据。

## 进程 CPU / 内存

只读取主验收采样；每约 200–220 ms 一次。下表按各探针 `startedAt` 至 `finishedAt` 裁切，包含突发测试尾部的 3 秒输入窗口，不是单个 IPC 耗时。CPU 为操作系统采样值，超过 100% 代表可能用了多核；短峰值仍可能漏采。

| --- | --- | --- |
| 1 MiB，第 1 次 | 25.0% / 132.2 MiB | 80.4% / 331.0 MiB |
| 1 MiB，第 2 次 | 35.0% / 128.6 MiB | 38.0% / 327.6 MiB |
| 8 MiB | 127.2% / 139.1 MiB | 120.4% / 714.9 MiB |
| 15 秒流式，第 1 次 | 13.3% / 139.4 MiB | 42.1% / 770.4 MiB |
| 15 秒流式，第 2 次 | 14.7% / 140.6 MiB | 40.3% / 676.4 MiB |

【事实】对应进程：主 App 51673，Go 51678，Node 51679，WebKit GPU 51681，Networking 51682，WebContent 51683。已用当前 `ps` 路径确认名字，不按 PID 猜角色。以上五个裁切窗口内，Go/Node 采样 CPU 峰值均为 0%；8 MiB 与后续流式时 Go RSS 约 23.9–24.1 MiB，Node 约 47.5 MiB。最后 10 秒输入成功一轮没有覆盖整个测试区间的进程采样，因此不拼凑 CPU 数字。

原始采样文件：

- `process-terminal-bursts-2026-09-04T08-37-30.799Z.json`：45 秒，207 个样本。
- `process-terminal-8MiB-and-stream-2026-09-04T08-39-26.675Z.json`：55 秒，254 个样本。
- `process-terminal-stream-keys-2026-09-04T08-40-27.920Z.json`：25 秒，115 个样本；未覆盖这 6 份探针的完整区间，不拿来给某次探针配对。
- `process-terminal-stream-keys-confirmed-2026-09-04T08-41-36.648Z.json`：25 秒，116 个样本。

【事实】8 MiB 加第一次流式的整段混合采样中，WebContent RSS 最高 770.4 MiB，结束约 601.7 MiB。第二次流式时从约 600.8 增至 676.4 MiB；本次没有做长期停稳和垃圾回收后的基线复测，不能把增长直接定性为内存泄漏。WebContent 还承载现有画布，RSS 不是终端独占内存。

【推断】本次终端输出压力主要出现在主 App 的传输/调度与 WebContent 的解析/界面侧，Go/Node 没有明显压力。Rust 外壳并没有消除 WebView/xterm 的工作量；仅凭 Rust 或构建成功无法得出整体流畅的结论。

## 会话与进程回收

【事实】主验收代理实机操作记录：改标题、切主题后 Shell 保持 PID 58797；五轮终端/助手切换后旧 PID 消失，新 Shell 为 60872。专项代理随后只读复核旧 PID 不存在、60872 为主 App 51673 的 zsh 子进程，未见其为僵尸；后续主验收继续关闭面板时，App 直接子进程只剩原 Go/Node。6 个探针 PID 均已自然退出，没有留存。

【事实】这是已执行的有限路径通过，不覆盖所有启动中取消、异常输出中关闭、仍有前台子进程时退出 App、强杀 fallback 或长期重复打开的场景。静态审查中关于 EOF 留存 session 和异常路径等待回收的风险仍应保留。

## 尚未关闭的高流量风险

【事实】这 6 轮每次最多约 8 MiB，因此没有触发隔离测试中约 50 MB 的 xterm 队列超限。`terminal-audit-evidence.md` 已复现的“write 抛错后 Channel 序号卡住”故障仍成立，不能因为有限负载通过而关闭。

【推断】建议先对该已证实故障补消费确认与可见错误终止，然后再做更长有限流式及同时拖动画布的验收。当前可以表述为“普通输出与已测 512 KiB/s 持续输出通过，8 MiB 突发尾部解析等待约 0.60 秒”；不能表述为“所有卡顿已经解决”。
